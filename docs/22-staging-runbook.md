# Staging runbook (UI + API + PostgreSQL on the VPS)

Status: **production deployed at `https://helpdesk.annabadigital.io`** (see *Production* below). The original staging plan follows. Target decided: the owner's VPS (Ubuntu 24.04, Docker, Coolify proxy on 80/443 with other apps already running), UI at `template-staging.annabadigital.io`, API and database private on the compose network (the UI proxies `/api/*` to them). Vercel and Azure were considered and dropped. No cloud resource, DNS record or secret has been created.

## What exists
| Artifact | Purpose |
|---|---|
| `api/Dockerfile` | Multi-stage .NET 10 image, runs as non-root, port 8080, `HEALTHCHECK` via `dotnet AnnabaDigital.Api.dll --healthcheck` (no curl in the runtime image). |
| `.github/workflows/ci.yml` | web (tsc, lint, vitest, build), api (dotnet test + image build), e2e (Playwright against a Postgres service). **Not yet run on GitHub**; first run is the PR that adds it. |
| `Api:BootstrapAdminEmail` | First-run bootstrap (see below). |

Verified locally: the image builds, boots in `Production` against an empty PostgreSQL, migrates, answers `/health` 200, returns 404 to `/api/*` without the proxy key, and issued the bootstrap invitation. Not verified: a real e-mail delivery, HTTPS, a real hosted database.

## Required configuration (API)
`ConnectionStrings__Default`, `Api__Origin` (https, the **UI's** public origin), `Api__ProxyKey` (≥ 32), `Security__CsrfKey` (≥ 32), `Security__PasswordPepper` (≥ 32), `Security__EncryptionKeys__1` (`openssl rand -base64 32`), `Security__CurrentKeyVersion=1`, `Email__Provider=resend`, `Email__ResendApiKey`, `Email__From` (a verified sender domain). The app refuses to start in Production without them.
Generate secrets once, store them in the host's secret store, never in the repo or the image. **Changing the pepper or encryption key later invalidates existing passwords/encrypted settings.**

## First start
1. Provision PostgreSQL 16 (managed, backups on, TLS).
2. Set `Api__AutoMigrate=true` for the first start **with exactly one instance** (it migrates and seeds roles/permissions; concurrent instances could race). Afterwards you may set it back to `false` and scale out, but then run migrations as a release step.
3. Set `Api__BootstrapAdminEmail=you@company.com`. With an empty database the API e-mails one normal super-admin invitation there. Open the link, set your own password, and enrol MFA straight away. Restarting before acceptance re-issues the invitation (the old link stops working). Once any user exists the setting does nothing; remove it anyway.
4. `Api__SeedDevUsers` must stay `false` (the API refuses otherwise).

## UI configuration
The UI container needs `API_URL` (`http://api:8080`, set in the compose file) and `API_PROXY_KEY` (same value as `Api__ProxyKey`). Both are read by `src/middleware.ts`, which also strips any client-supplied proxy key. Without `API_URL` the UI answers 404 for `/api/*`.
Network: the API and database are not published, so only the UI can reach them. `Api__Origin` must equal the exact public origin of the UI, or CSRF origin checks reject every write. (If the UI is hosted elsewhere, e.g. Vercel, publish the API on its own domain and set `API_URL` there instead.)

## Checks after deploy
`/login` 200 (API health is internal: the compose healthcheck gates the UI) · sign in with the bootstrap admin · MFA enrolment · invite a user and confirm the e-mail arrives (this is the first time the Resend adapter meets the real service) · `/audit` shows the events.

## Open decisions (recommended defaults)
- **Hosting target**: recommend Azure Container Apps (single replica to start) + Azure Database for PostgreSQL Flexible Server. Needs your confirmation and an Azure subscription.
- **Multiple replicas**: the dispatcher and rate limiter are database-backed, so scaling out is safe once migrations are no longer run at boot.
- **Log retention / alerting on failed e-mails**: there is no admin view for `outbox_emails` yet.

## E-mail without Resend (SMTP)
The API has three senders: `console` (development), `resend`, and `smtp` (MailKit, any server). Select with `EMAIL_PROVIDER` (compose default `smtp`); Production refuses `console` and plain (unencrypted) SMTP.
| Route | Setup | Limits / notes |
|---|---|---|
| **Gmail SMTP** (quickest, no domain work) | Google account with 2-step verification → create an **App Password**. `SMTP_HOST=smtp.gmail.com`, `SMTP_PORT=587`, `SMTP_SECURITY=starttls`, `SMTP_USERNAME=<gmail>`, `SMTP_PASSWORD=<app password>`, `EMAIL_FROM=Annaba Digital <the same gmail>` | ~500 recipients/day; Gmail rewrites any other From address; fine for staging, not for production volume. |
| **Another SMTP relay** (Brevo, Amazon SES, Mailgun…) | Same variables with the provider's host/credentials; verify the sending domain there | Free tiers exist; this is still a third party, just not Resend. |
| **Own mail server on the VPS** (Postfix, docker-mailserver, Stalwart) | `SMTP_HOST=<container or host>`, port 587/465 with TLS | Outbound ports 25/465/587 are open from the VPS (checked 2026-11-06). Needs, before mail is trusted: reverse DNS (PTR) set in the VPS panel to the mail host (currently `srv2076557.hstgr.cloud`), SPF, DKIM and DMARC TXT records for `annabadigital.io` (none exist today), and some IP warm-up. Expect spam-folder delivery until then. |
The queue (`outbox_emails`) retries a failed send 3 times, then gives up and wipes the body; fix the credentials and restart `api` to re-issue the bootstrap invitation.

## Single sign-on (OpenID Connect)
Optional and off by default. Set `SSO_ISSUER`, `SSO_CLIENT_ID`, `SSO_CLIENT_SECRET` (and `SSO_DISPLAY_NAME`) in Coolify, then redeploy `api`; the login page then shows "Sign in with …".
- Register this redirect URI at the provider: `https://<your-origin>/api/auth/sso/callback`. It uses the authorization-code flow with PKCE; the secret stays on the server.
- Nobody is created by SSO. A person signs in only if the provider reports a **verified** e-mail that matches an existing **active** user (invite them first). The first sign-in links the provider's stable subject to that user; afterwards the subject decides, not the e-mail, and a different account claiming the same e-mail is refused.
- MFA, suspension and lockout apply exactly as for a password sign-in. Passwords keep working.
- Microsoft Entra does not send `email_verified`: set `SSO_REQUIRE_VERIFIED_EMAIL=false` only when the Entra tenant already controls who can sign in.
- Every attempt is audited (`auth.sso.link`, `auth.sso.denied`, `auth.login.success` with `method=sso`).
- Not verified against a real provider yet: try it with a test client first (the unit and endpoint tests use a stand-in provider).

## Multi-tenant
One database, shared schema: users, roles, invitations, sessions, audit/security events, access requests and reviews carry a `tenant_id`, and every query is filtered to the signed-in person's tenant (a global EF filter) while new rows are stamped with it. Each user belongs to exactly one tenant; e-mail addresses are unique across all tenants.
- The existing data moves to the **default tenant** (the platform tenant) by the `MultiTenant` migration. Take/verify a backup first.
- Only Super Admins of the platform tenant see **Administration → Tenants**: creating a tenant copies the system roles into it and e-mails its first Super Admin an invitation. Suspending a tenant ends its sessions and blocks sign-in until re-activated.
- System settings (password policy, sessions, e-mail, SSO) are global, so only the platform organisation may read or change them (`/api/settings*` answer 403 to any other tenant; the UI hides *System Settings*). Public self-registration and SSO sign-in resolve to the platform tenant / the matching user's own tenant respectively; other tenants onboard by invitation.
- The e-mail outbox is per tenant too (`outbox_emails.tenant_id`, migration `OutboxEmailTenant`): *Email Delivery* lists only the signed-in organisation's mail. Mail sent without a signed-in tenant (password reset, verification, accepting an invitation) is filed under the recipient's organisation. The e-mail dispatcher itself is not scoped and sends everyone's mail.
- Audit events are append-only in the database, so the one `invitation.accept` row created on staging before this fix (tenant `pt-aplikasi-indonesia`'s first admin) stays filed under the default tenant; new rows are stamped correctly.
- Anonymous flows (sign-in, registration, invitation accept, password reset, workers) run unscoped by design and find rows by unique values; every authenticated request is scoped. Tests in `TenantTests` cover cross-tenant reads/writes (404), audit stamping, and suspension.

## GA Helpdesk: capacity, PostgreSQL settings and the load test
- **Extension.** Migration `SearchAndQueueIndexes` runs `CREATE EXTENSION IF NOT EXISTS pg_trgm` (ticket search). It is part of PostgreSQL's standard contrib set (the official `postgres:16` images include it) and is a *trusted* extension, so the database owner may create it; a managed database that forbids it must have it enabled by the provider first. Without it the migration fails and the API does not start.
- **Settings.** The defaults of a fresh PostgreSQL (`shared_buffers = 128MB`, `work_mem = 4MB`) are far too small for a large tenant. Measured on 500,000 tickets, setting `shared_buffers` to about a quarter of the machine's RAM, `effective_cache_size` to about half, `work_mem` 16 MB and `max_connections` above the API's pool size (default pool 100) made the difference between "queue p95 about 1.8 s" and "about 0.1 s" under 100 people. Tune these on any server that will hold more than a few tens of thousands of tickets.
- **The connection string** gets `-c plan_cache_mode=force_custom_plan` appended by the API itself, so every statement is planned with its real values (needed for the per-tenant filter to use the tenant indexes). Do not override it.
- **Load test.** `scripts/load-seed.sql` builds a throw-away database with hundreds of thousands of tickets; `scripts/load-test.mjs` signs in as three roles and runs a realistic mix against the API, printing p50/p95/p99 per request against the PRD budgets and exiting non-zero when one is broken (`docs/35-ga-helpdesk-slice12-report.md` has the exact commands and the numbers measured). Run it against a copy of the real hardware before a pilot, never against production.
- **Counting stops at 10,000.** Lists show "10,000+" past that; the exact number of a huge result is not worth making every search slower.

## GA Helpdesk: data retention and legal holds
- **Off by default.** Until an administrator opens *Administration → Data Retention*, switches the policy on and saves it, nothing is ever removed from tickets, files or notifications. Needs the permission `retention.manage` (Super Admin has it; give it to a custom role for whoever owns privacy — it is not in GA Manager). Saving, running and placing or releasing a legal hold each need a fresh password check and are audited.
- **When it runs.** The existing daily `RetentionWorker` (`Retention__Enabled`, `Retention__IntervalHours`, `Retention__StartupDelayMinutes`) now also applies every organisation's own policy after the audit/credential housekeeping. At most 5,000 tickets and 5,000 files per organisation per run (the rest follows the next day; the run says `more`). An administrator can also use *Run now*. Several API instances are safe: each step only touches rows that still match.
- **What it removes.** Finished tickets only (closed, cancelled, rejected), aged from the last update, which for them is the day they finished. *Anonymise* removes the subject, description, answers, resolution/hold/cancel text, every timeline body and name, approval comments and addresses, the ticket's notifications and its files; the ticket stays as a statistic and can no longer be reopened. *Delete* removes the ticket with its timeline, approvals, notifications and file rows. Files go first (bytes, then the row is marked): a file that cannot be deleted (a locked or read-only volume) is reported (`retention.files_failed` security event, `filesFailed` in the last-run summary), retried at the next run, and holds its ticket back until it is gone.
- **Legal hold.** A ticket under hold is skipped by every step and its files cannot be removed by hand. Holds survive until released.
- **Backups.** A database dump or volume snapshot still contains what was removed until that backup itself expires. After restoring an old backup the policy (also restored) removes what is due at the next daily run. Files on the volume that no row refers to (a newer volume with an older database, or a crash between two steps) are found and removed by *Stored files* on the same page.
- **Not covered by the policy:** audit and security logs (platform setting `auditRetentionDays`, shown on the page), the user accounts themselves (see *Download my data and account closure*), e-mails already sent.

## GA Helpdesk: attachments, virus scanning, workers and go-live
**Attachments (docs/30).** Bytes are written to `Storage__Path` (compose: `/data/files` on the `annaba-digital-files` volume, created and owned by the API's non-root user in the image). Production **refuses to start** unless the path is absolute **and** either `Storage__ClamAvHost` points to a ClamAV daemon or `Storage__AllowUnscanned=true` records a deliberate decision to go without (compose variables `CLAMAV_HOST`, `ALLOW_UNSCANNED_UPLOADS`). An existing staging deploy therefore needs one of the two set before its next release.
- **Scanner.** Uncomment the `clamav` service in `deploy/docker-compose.coolify.yml` (about 1.5 GB RAM; the first start downloads signatures, allow several minutes) and set `CLAMAV_HOST=clamav`. The API talks to clamd over TCP 3310 (INSTREAM), refuses a file that is infected **or** cannot be scanned (fails closed; the API log says "ClamAV is unreachable"), and audits refusals as `attachment.rejected`. Check: upload the EICAR test string saved as `eicar.txt` — it must be refused; then stop the `clamav` container — every upload must be refused until it is back.
- **Backups.** The database dump does **not** contain the files, so the compose `backup` service now also writes `annaba_digital-<stamp>.files.tgz` (a tar of the files volume, mounted read-only) right after each dump, with the same stamp; `deploy/pull-backups.sh` copies both. See *Restore drill and the files check* below. A dump restored without its files shows attachments whose bytes are missing (downloads answer 404).
- **Workers** (one instance of the API runs them; do not scale the API out without a leader lock): auto-close of resolved tickets, SLA clock and escalations, e-mail outbox, and the daily purge of uploads nobody attached (older than 24 h). If SLA states look frozen or notifications are not sent, look for a worker error in the API log first.
- **Request size.** The UI proxy buffers up to 10 MB per request; files are limited to 8 MB. Raise both together if you ever raise the limit.

**Go-live for a new organisation (ADM-001).** Sign in as the organisation's administrator → *Helpdesk Setup → Get started*. The page lists the six required steps; **Quick start** creates the first site, the first team (choose the people who will work tickets — invite them and give them *GA Agent* first), service levels and a rule that sends every request to that team. Then: file a test request from a normal account and follow it through the queue; read the checklist's advice items (approvals, scanner, test request). The GA Manager role can do all of this without being a user administrator.

**Demo data (development and staging only).** `node scripts/demo-data.mjs` signs in through the API as the seeded dev accounts and creates a setup, a few places and about ten requests in different states, marked "[Demo]". It refuses any host other than localhost without `--yes` and needs the dev accounts (`Api__SeedDevUsers`, Development only), so on a Production-configured server it cannot run. Never run it on a customer's live tenant.

## Restore drill and the files check
**Drill (do it before a pilot, and after every change to the backup setup).** `deploy/restore-drill.sh <dump> [files.tgz]` restores a dump into a throw-away PostgreSQL container (never a real database), unpacks the files archive into a temporary folder and checks that every live attachment row has its bytes. It prints the latest migration and the row counts, lists missing files, and exits 0 (usable), 1 (restore failed or bytes missing) or 2 (bad input); the container and folder are removed afterwards. `PG_IMAGE` selects the server image (use your production major version). Without the archive it checks the database only and says that files were not checked.
- **Verified locally:** a dump of the e2e database (5 organisations, 15 users, 14 tickets, migration `DataRetention`) with its files archive passed (3 attachments, 0 missing); the same dump with an archive lacking one file failed and named the file; a database-only run passed with the warning; a non-dump was refused (exit 2); no container was left behind. The compose `backup` step (`tar czf` of the volume, then rename) was run in the `postgres:16-alpine` image against a real folder and the archive verified.
- **Not verified:** on Coolify (the volume names carry the project prefix; the backup service now mounts `annaba-digital-files` read-only, so redeploy once and wait for the next dump to see a `.files.tgz` in `annaba-digital-backups`), a restore across Postgres minor versions, and a real full recovery of the VPS.
**Real recovery order.** Stop `api`; create an empty database and `pg_restore` the dump; unpack the *matching* `.files.tgz` into the files volume (`tar xzf <file> -C /data/files`); start `api`; sign in as an administrator with `retention.manage` → *Administration → Data Retention → Stored files → Check stored files*. **Missing** = rows whose bytes are not on the volume (it lists the first 50 with their tickets). **Unreferenced** = bytes no live row refers to (uploads that never finished, files newer than the restored database, bytes left by a crash); *Remove unreferenced files* deletes only those older than an hour, never another organisation's folder, and is audited (`files.orphans.clean`, fresh password check). The dump is taken first and the archive right after it, so rows never point at files created after the dump; the only expected drift is files removed in between (reported as missing for rows that no longer matter) and files uploaded in between (unreferenced).

## Backups, auto-deploy and monitoring
**Backups (in the compose file).** The `backup` service runs `pg_dump -Fc` 30 s after start and then every `BACKUP_INTERVAL_HOURS` (default 24), writing `annaba_digital-YYYYmmdd-HHMMSS.dump` into the `annaba-digital-backups` volume, and prunes dumps older than `BACKUP_KEEP_DAYS` (default 14). Its healthcheck turns unhealthy when no dump is younger than two intervals. A dump is written to a `.tmp` name first and renamed only when `pg_dump` succeeds.
- **Restore** (into an empty database; do this on a copy first): `docker exec -i <backup-container> pg_restore -h db -U annaba_digital -d <target_db> /backups/<file>.dump`. For a full recovery stop `api`, create a fresh database (or recreate the volume), restore, then start `api`. The secrets (`SECURITY_PASSWORD_PEPPER`, `SECURITY_ENCRYPTION_KEY`) must be the same as when the dump was taken, or passwords and encrypted settings will not work.
- **Off-site copy (required for a real backup).** The volume lives on the same VPS, so losing the VPS loses the backups too. From your own machine run `deploy/pull-backups.sh` (load the key with `ssh-add` first). It finds the current `backup` container (the name changes on every redeploy), copies only dumps you don't have yet to `~/annaba-vps-backups` (mode 700, outside the repo), checks each file's `PGDMP` header, and deletes local copies older than `KEEP_LOCAL_DAYS` (default 60). It only reads on the VPS. Override `VPS_HOST`, `BACKUP_DEST`, `KEEP_LOCAL_DAYS` through the environment. It needs a non-interactive ssh, so a scheduled run (cron/launchd) needs a key the agent can use without a prompt; until then run it by hand, e.g. weekly and before each deploy that changes the schema. The copies hold user data (e-mail addresses, password hashes): keep them on an encrypted disk.
  Verified: the script fetched 11 dumps from staging, a second run fetched none, and the newest dump restored into a scratch database (1 user, 1 tenant, latest migration `MultiTenant`). Not verified: a scheduled run, or a restore into a Postgres of a different minor version.
- Verified locally: a dump was taken, restored into a fresh database (50/50 rows), and the retention rule removed only an old file. Not verified: on Coolify, and restoring a dump from a different Postgres minor version.

**Auto-deploy (Coolify).** Resource → Configuration → *Advanced* → enable **Auto Deploy** (needs the GitHub App source). With a deploy key or public repo instead, copy the *Webhook* URL from the resource's *Webhooks* tab into GitHub → repo Settings → Webhooks (event: push, content type JSON, secret as shown). Pushes to `main` then redeploy by themselves; consider protecting `main` so only reviewed PRs land there.

**Monitoring.** (a) Coolify → *Notifications*: enable Email (SMTP, same Gmail settings) or Telegram/Discord for deployment results and *container stopped/unhealthy* events. (b) An external uptime check on `https://template-staging.annabadigital.io/login` every 5 minutes (e.g. UptimeRobot free tier) catches a down proxy or VPS, which Coolify cannot report about itself. (c) The compose healthchecks (`db`, `api`, `ui`, `backup`) are what Coolify uses to mark the resource unhealthy.

## Approval notifications
When e-mail is configured, anyone who may assign roles (`users.assign_role`, up to 25 people per event, never the person who caused it) gets an e-mail when an access request is submitted or an access review is opened, and the requester is told when their request is approved or rejected. Mail goes through the outbox, so a mail problem never fails the request itself. The sidebar shows a count of requests and review items waiting for the signed-in person (their own are not counted), refreshed every minute from `GET /api/access-requests/pending-count`. ## Scheduled access reviews
*Access Reviews → Schedule* (permission `users.assign_role`, one schedule per organisation) opens a review by itself every month, 3 months, 6 months or year, with 1–90 days for reviewers to finish. The review is identical to a manual one (snapshot of every active user's privileged roles) and shows "Scheduled (automatic)" as its starter; reviewers (everyone who may assign roles) are e-mailed when it opens. Switching it on, or changing the period, sets the next run one period from now. A background worker checks hourly (`ReviewScheduler__Enabled`, `ReviewScheduler__IntervalMinutes`, `ReviewScheduler__StartupDelaySeconds`); a schedule is claimed with one UPDATE so several API instances never open the same review twice. If a review is still open when one is due, that run is skipped (reviews never stack) and the next is a period away; suspended organisations are skipped the same way. New table `access_review_schedules` (migration `AccessReviewSchedule`). Verified by tests with a created tenant; not verified: a real wait through a full period on staging.

## Platform support mode (tenant switcher)
On *Administration → Tenants* a platform Super Admin can press **Manage** on another tenant (`POST /api/tenants/{id}/support`, needs `tenants.manage`, the platform organisation, a fresh re-authentication, and an active tenant). From then on, in the same session, the admin screens (users, invitations, roles, permissions, access matrix, audit, security events, access requests queue, access reviews, admin dashboard, all sessions, email deliveries, avatars) show **that** tenant; everything about the signed-in person (sign-in state, profile, MFA, own sessions, own requests), the Tenants page and System Settings stay in their own organisation. An orange banner and sidebar chip show the mode; **Exit support mode** (`POST /api/tenants/support/exit`) leaves it. It also ends by itself after 2 hours, when the tenant is suspended, or if the person is no longer in the platform organisation.
Transparency: entering and leaving write an audit row in the platform's trail and one in the tenant's trail, plus a *support.access* security event the tenant's administrators see; every action taken inside is recorded in the tenant's audit trail with the actor labelled "(platform support)". The person acts with their own permissions (Super Admin), so the hierarchy and anti-escalation rules apply as usual. Session columns `acting_tenant_id`, `acting_since` (migration `TenantSupportMode`). Not verified: staging, and a tenant administrator's view of the events in the UI.

## Per-organisation security policy
*Administration → Security Policy* (permission `settings.manage`, for every organisation except the platform one, which keeps using *System Settings*) lets an organisation be **stricter** than the platform on: minimum password length, breached-password check, failed sign-ins before lock, lock duration, two-step verification policy, re-authentication for critical changes, idle timeout, longest session, "remember me" windows and invitation expiry. The platform's value is the default and the loosest allowed: a weaker value is refused with the reason, and a value equal to the platform's means "follow the platform". Reading applies the same rule again (stricter of the two), so if the platform tightens later an older, looser choice is raised automatically. Not tunable per organisation (stay platform-wide): registration mode, e-mail sender and key, single sign-on, audit retention.
Where it applies: sign-in lockout, session lifetimes and the MFA-required gate use the person's own organisation (also for anonymous sign-in, SSO and password reset); password rules use the organisation of the person or of the invitation; invitation expiry and critical-action re-authentication use the organisation of the request. `GET/PATCH /api/settings/tenant`, table `tenant_settings` (migration `TenantSettings`, only overrides are stored), audit action `settings.tenant.update` plus a `policy.change` security event, and it needs a fresh re-authentication. A platform administrator in support mode edits the supported organisation's policy. Caution: choosing two-step verification "required" asks every person without it to enrol at next sign-in, the administrator who saves it included. The public sign-in/registration screens still show the platform's minimum length as their hint; the server enforces the organisation's.

## Account recovery by an administrator
New critical permission `users.reset_credentials` (Super Admin has it; give it to other roles deliberately). On a user's *Security* tab, **Reset two-step verification** removes their authenticator and recovery codes (for someone who lost the phone and every code) and **Require new password** makes their current password stop working for sign-in until they choose a new one through a one-time e-mailed link (30 minutes; "Forgot password" issues a new one). Both need a fresh re-authentication, obey the hierarchy rule (not for someone who holds permissions you don't), refuse yourself (use your profile), only apply to active accounts, sign the person out everywhere, e-mail them, and are audited (`user.mfa.reset`, `user.password.require_reset`, with the reason) with a security event (`mfa.reset` High, `password.reset_required` Medium). The administrator never sees or sets a password. If the policy requires two-step verification the person enrols again at next sign-in. Sign-in answers `password_reset_required` (the right old password, no session issued) while `credentials.must_change` is set; it clears when the new password is set through the link or the profile. Needs e-mail to be configured. Not verified: real e-mail delivery on staging.

## New-device sign-in alert
When someone signs in (password or single sign-on) from a device and browser they have not used in the last 90 days, they get an e-mail with the device, browser, IP address and local time (their profile time zone) and a link to *Profile → Security*. The very first sign-in of an account never alerts (nothing to compare with). It follows the existing *Profile → Notifications → Security alerts* switch (on by default); the audit entry `auth.login.success` carries `newDevice=true`, and no security event is raised so the bell isn't flooded. Device and browser are the coarse labels already stored on sessions (e.g. "iPhone · Safari"), so the comparison is only as precise as those labels, and sessions older than the retention purge are forgotten (a device may look new again). It is best effort and never blocks the sign-in. Needs e-mail to be configured. Not verified: real e-mail delivery on staging.

## Download my data and account closure
*Profile → Privacy*. **Download my data** (`GET /api/me/export`, fresh password check, audited as `account.export`, `Cache-Control: no-store`) returns one JSON file: account, profile and preferences, roles, security summary (MFA on/off, password changed, SSO providers), up to 200 sessions, up to 1,000 of the person's own audit entries, their access and closure requests, and (slice 13) the helpdesk requests they made, their own public comments and the names of files they attached. It never contains the password hash, authenticator seed, recovery codes, tokens or other people's data.
**Close my account** (`POST /api/me/closure`, fresh password check) creates a request that administrators who may suspend accounts (`users.suspend`) see under *Identity & Access → Account Closures* (they are e-mailed; nobody decides their own; the hierarchy rule applies; the last active Super Admin can't be closed). Approving starts a 14-day waiting period (`AccountClosureService.WaitDays`) in which the person can still sign in and cancel (`POST /api/me/closure/cancel`). A background worker (`AccountClosureWorker`, hourly, same `ReviewScheduler__*` switches) then, per organisation and claimed inside one transaction so instances never double-close: deletes the person's sessions, MFA, linked sign-ins, tokens, picture, credentials and roles, deactivates the user, replaces the name with "Closed account" and the e-mail with `closed-<id>@closed.invalid`, clears phone/department/job title, and e-mails the original address a confirmation. The user row stays so history keeps resolving; if they became the last Super Admin during the wait the closure is cancelled instead. New table `account_closure_requests` (migration `AccountClosureRequests`; one open request per person).
Limits: audit entries are append-only in the database, so the old name/e-mail inside past audit rows (`actor_label`, event details) stays for the audit retention period; outbox e-mail rows already sent keep only the recipient and subject until the retention purge. Not verified: a real 14-day wait on staging and e-mail delivery.

## Dark mode
A sun/moon button in the top bar switches between light and dark; *Profile → Notifications → Appearance* adds "Same as device" (follows the operating system live). The choice is kept in the browser (`localStorage` key `annaba-digital-theme`), so it is per device, not per account, and a tiny inline script in `layout.tsx` applies it before the first paint (no flash). New CSS should use the variables (`--surface`, `--tint`, `--hover`, `--ink-*`, `--*-ink`, `--*-line`) rather than hex colours. Charts use the variables for axis text and grid lines; series colours stay the same in both themes. axe checks the same pages in both themes (`e2e/quality.spec.ts`). ## Bahasa Indonesia (language)
Two languages: English and Bahasa Indonesia. Before sign-in the choice is the switch on the sign-in screens (kept in the browser, `localStorage` `annaba-digital-lang`; first visit follows the browser language). Signed in, the person's own *Settings → Language* (stored on the account, returned as `language` by `/api/auth/me`) wins and the whole page tree re-renders on change. Code calls `t("English text")` from `@/i18n`: **the English text is the key**, so a missing translation simply shows English; `{name}` placeholders are filled from the second argument. Translations live in `src/i18n/id.ts`; dates, relative times ("5 menit lalu") and the date locale follow the language (`lib/format.ts`). To translate a new string: wrap it in `t()` (JSX text and `label`/`title`/`description`/`placeholder`… props are easy to wrap; module-level constants must be translated where they are rendered, not where they are defined) and add the Indonesian line to `id.ts`.
Covered: navigation, shell, sign-in/registration/reset/verification/MFA/locked/invitation screens, dashboard, users (overview, list, detail, invitations), profile (all tabs), settings, the administration pages (roles, permissions, access matrix, audit, security events, sessions, access requests/reviews/closures, tenants, security policy, system settings, e-mail delivery) and shared components (tables, pagination, filters, confirmations, errors). Not translated yet: **messages that come from the server** (validation and error messages; system role descriptions are translated but custom role names/descriptions are data).
E-mail is bilingual: every template in `EmailTemplates` carries English and Indonesian wording, and the outbox picks one when the mail is queued: the recipient's own profile language (*Settings → Language*), else the sender's hint (an invitation is written in the **inviter's** language, because the invitee has no profile yet), else English (for example the verification mail of public self-registration). Add a template by writing both `Copy` texts. Mail already queued before this change stays as it was written. Not verified: a native-speaker review of the translations.

## End-to-end review notes (hardening)
- **Web app headers.** The UI (Next.js) now sends `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`, HSTS and a CSP limited to `frame-ancestors 'none'; base-uri 'self'; form-action 'self'; object-src 'none'` (the static part; the script policy is added per request, see **Script CSP** below) and no `X-Powered-By`. The API already sent its own. Before this, the login page could be framed.
- **Single sign-on state** is sealed with the application's own encryption key (`ISecretProtector`, same key as MFA secrets) instead of ASP.NET Data Protection, whose key ring lived inside the container and was lost on every redeploy (a sign-in in flight during a deploy failed, and several instances could not read each other's cookies). Unreadable cookies are treated as "no flow".
- **Account closure** now also blanks the e-mail and message on the invitation(s) that carried the person's address. Still kept by design: audit rows (append-only), security-event text, free-text reasons on access/closure requests, outbox rows until the retention purge.
- **Indexes** `(tenant_id, ts)` on `audit_events` and `security_events` (migration `TenantEventIndexes`) for each organisation's audit lists; two multi-collection user queries use split queries (an EF warning in the staging log).
- **Tooling.** `npm run lint` ignores build output (it reported ~11,000 problems from `.next`); the review scheduler/closure worker are disabled in the test host; vitest covers `t()` and relative dates.
- **Known and accepted for now.** `npm audit` reports a PostCSS advisory inside Next 15 (build-time CSS tooling; the fix is Next 16, a major upgrade). Settings are read a few times per request (global, organisation, platform flag); a per-request cache would cut queries but was left alone. Both background workers share the `ReviewScheduler__*` switches.

## Performance and caching
Measured with a SQL command counter (`CommandCounter`, also the basis of `QueryBudgetTests`): before, an authenticated request spent 5–6 queries before doing any work, and some pages were far worse (`/api/users/stats` 29 queries, `/api/dashboard/admin` 40). Now `/api/auth/me` 6, `/api/roles` 3, `/api/audit` 4, `/api/access-matrix` 3, `/api/users/stats` 7, `/api/dashboard/admin` 18, `/api/settings/public` 1.
What changed: (1) head-counts on the user overview are one aggregate query (status counts, locked, unverified and the 12 monthly growth points) instead of one query each; the dashboard's sign-in chart is grouped by day in the database instead of loading every sign-in event of the last two weeks; (2) **short-lived in-process cache** (`AppCache`, default 30 s, `Cache__Seconds`, 0 = off) for system settings, each organisation's effective policy and each organisation's status (15 s); anything that saves settings, organisation settings or an organisation clears it at once on that instance, **other instances see a change within the time limit** (so a changed lockout or MFA policy can take up to 30 s to reach every instance; suspending an organisation also revokes its sessions immediately); (3) a **per-request memo** of a person's permissions in `AuthorizationService`, dropped the moment anything that decides permissions (users, roles, role permissions, assignments) is saved; permissions are never cached across requests.
Not changed: the session check still reads the database on every request (that is the security guarantee), the e-mail outbox still writes synchronously, and the Indonesian dictionary ships in the main bundle (about 12 KB gzipped). Web bundles are small (103 kB shared, 129–149 kB first load per page).

## Script CSP (nonce)

- `src/middleware.ts` adds a per-request nonce policy to every page: `script-src 'self' 'nonce-…' 'strict-dynamic'` (no `unsafe-inline`, no `unsafe-eval` in production), `connect-src 'self'`, `frame-src 'none'`, plus the framing/base/form/object rules. Next stamps the nonce on its own scripts; the theme script in `layout.tsx` reads `x-nonce`. Pages are therefore rendered per request (no static caching). Styles still allow `unsafe-inline` (inline `style` attributes); tightening that is a separate step.
- **`CSP_MODE`** (UI container env): unset or anything else = **report-only** (`Content-Security-Policy-Report-Only`, nothing is blocked); `enforce` = blocking. Default is report-only so the policy can be watched on staging first. Playwright runs with `enforce`, so any blocked script fails the e2e suite.
- Violations are posted to `/csp-report` and written to the UI container log as `[csp-violation] …` (read them in Coolify logs). Rollout: deploy in report-only, use the app for a few days (login, MFA, admin screens, PWA install), confirm no `[csp-violation]` lines, then set `CSP_MODE=enforce` and redeploy. Rollback is removing the variable.
- Adding a third-party script, font CDN or API host later means extending `buildCsp`; the unit test `csp.test.ts` and the e2e "no CSP violation" test will flag what was missed.
