# Modul `assets` — aset, vendor, checklist, pemeliharaan preventif

File: `scripts/demo/03-assets.mjs` (± 80–120 detik pada database kosong; dijalankan ulang aman: semua dicari dulu berdasarkan nama/tag, tidak ada duplikasi).
Sampel impor: `scripts/demo/samples/assets-import.csv` (dengan satu baris salah) dan `assets-import-corrected.csv` (semua benar). Kedua file **ditulis ulang oleh modul** setiap kali dijalankan supaya tanggalnya relatif terhadap hari seeding.

Semua data dibuat lewat API oleh: hendra (tipe aset, sebagian besar aset, vendor, checklist, rencana), admin/Sarah (sebagian aset dan riwayatnya), putri (sebagian rencana, biaya), agus/bayu/joko (mengerjakan work order). Angka di bawah adalah hasil run pada hari seeding; semuanya relatif terhadap hari itu.

## Not demonstrable / bugs / caveats

- **Pengingat kontrak/garansi dikirim worker latar belakang** (`TicketAutoCloseWorker`: pertama ± 135 detik setelah API start, lalu tiap 60 menit; tidak ada endpoint untuk memicunya, jadi modul ini tidak bisa memicunya). Saya mengujinya: restart API (tanpa reset) lalu tunggu ± 2,5 menit → hendra dan Sarah menerima 3 pemberitahuan kontrak (Daya Listrik "berakhir pada …", Bersih Hama dan Cakra "telah berakhir") dan 1 ringkasan garansi ("8 asset warranties end soon or have ended"). Pada seeding penuh worker pertama kemungkinan berjalan sebelum modul ini selesai, sehingga pengingat baru muncul ± 1 jam setelah API start. **Saran: restart API setelah seed selesai (tanpa reset) dan tunggu 3 menit sebelum demo.** Worker yang sama menutup otomatis tiket *resolved* > 3 hari dan menjalankan generator pemeliharaan (idempoten; tidak membuat duplikat, sudah diuji).
- Tidak ada status "hilang" pada aset (hanya in_use, in_repair, stored, retired). Aset hilang = *retired* dengan alasan "hilang …".
- **ga_supervisor (putri) dan ga_agent tidak punya `assets.manage`, `vendors.manage`, `assets.import`**: hanya ga_manager (hendra) dan super_admin yang bisa menambah/mengedit aset, menyerahkan/memindahkan, impor CSV, mengelola vendor. Putri hanya membaca aset dan vendor, tetapi mengelola rencana pemeliharaan dan work order. Semua alur aset di atas dijalankan hendra.
- **Tiket pemeliharaan terencana dihitung sebagai "request tentang aset"**: aset dengan ≥ 3 tiket dalam setahun mendapat petunjuk *frequent* ("ganti daripada diperbaiki?") dan masuk grafik "Most requests". Akibatnya AC-SRV-01 (7 tiket) dan GEN-001 (9) tampil "sering bermasalah" (filter *frequent* hanya mengembalikan keduanya) dan mendominasi grafik "Most requests", padahal itu servis rutin. Ini perilaku aplikasi, bukan hasil seed. Saya menjaga AC-GRD-01, aset AC Level 3 dan APAR di bawah ambang (≤ 2 tiket pemeliharaan) supaya tiket gangguan dari modul servicedesk yang membuatnya "frequent". Sebaiknya servicedesk memberi 3+ tiket gangguan pada satu aset yang relevan (mis. PRN-002 atau AC-REC-01).
- Nomor tiket: tiket pemeliharaan memakai nomor pertama (GA-2026-000001 …), urut menurut tanggal jatuh tempo; tiket modul servicedesk bernomor lebih besar walau tanggalnya (backdate) bisa lebih lama.
- Tiket pemeliharaan lama berstatus *closed* tanpa baris "closed" di timeline (ditutup lewat SQL karena > 4 hari); tiket yang selesai ≤ 4 hari lalu berstatus *resolved* dan akan ditutup otomatis oleh worker. Pemohon tiket-tiket ini adalah pemilik rencana (putri/hendra).
- Rating vendor kosong (rating datang dari tiket yang dinilai pemohon, modul servicedesk). Pest control dan pembersihan oleh vendor tanpa pengguna portal dikerjakan "atas nama vendor" oleh bayu/putri (work order tercatat dengan pelaksana bayu/putri dan vendor terisi).
- Compliance dihitung dari tanggal seeding (jumlah visit sedikit berubah menurut hari). Tanggal jatuh tempo "beberapa hari lagi" bisa jatuh di akhir pekan (rencana berbasis tanggal kalender, bukan hari kerja).
- Ditambahkan 3 layanan *staff-only* ke katalog (Fire safety inspection, Vehicle service, Office equipment service) karena rencana harus "difile" pada sebuah layanan dan katalog awal tidak punya padanannya. Layanan staff tidak muncul di portal karyawan.
- Tidak diverifikasi di UI (Next.js) — hanya lewat API sebagai persona yang membuka layar tersebut; log API sandbox kosong (stdout di-buffer).

## Backdating done (SQL, hanya baris yang dibuat modul ini)

- `assets.created_at/updated_at` = tanggal beli + beberapa hari (atau tanggal cerita); `asset_events.created_at` untuk "Added to the register" sama; langkah riwayat aset featured (serah-terima, pindah, repair, retire) diberi tanggal 5–1600 hari lalu menurut urutan kejadian, jam kerja Jakarta.
- Untuk tiap visit pemeliharaan lampau (37 visit): rencana dipaksa sebentar menjadi "tahunan mulai dari tanggal itu, lead 0" (`maintenance_plans.unit/every/starts_on/next_index/next_due_on/lead_days`) dan disimpan lewat API supaya **generator aplikasi** membuat tiket + work order; dikerjakan lewat API oleh agus/bayu/joko/putri (start, centang tiap baris checklist, foto, catat waktu, biaya, complete). Lalu `tickets` (created/updated/resolved/first_responded/assigned/closed), `ticket_events` (disebar proporsional antara dibuat dan selesai), `work_orders` (created/started/completed), `work_order_tasks.done_at`, `work_order_times` (created_at, work_date), `work_order_costs.created_at`, `attachments.created_at`, `maintenance_visits.created_at` dan `notifications` (created, read) digeser ke tanggal jatuh tempo (tepat waktu = selesai pada/sebelum hari kerja terakhir ≤ tanggal itu; terlambat = 1–3 hari kerja sesudahnya). Tiket yang selesai > 4 hari lalu di-set `closed`.
- Setelah itu jadwal asli dikembalikan (SQL) dan rencana disimpan sekali lagi lewat API: generator sendiri mencatat tanggal tanpa visit sebagai **missed** (2 visit: genset, pest control gudang) dan membuat visit yang sedang berjalan; `maintenance_visits.created_at` visit missed = hari sesudah tanggalnya; tiket/WO/notifikasi visit terbuka diberi `created_at` = (jatuh tempo − lead) 07:05, notifikasinya tetap belum dibaca (sengaja).
- Tidak digeser: `audit_log` (berstempel hari seeding).
